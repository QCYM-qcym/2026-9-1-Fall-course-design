# 文档体系实施设计

## 1. 建设目标

为《山东省气象预报数据可视化系统的设计与实现》建立适合两人、两周完成的前期软件工程资料。成果用于统一需求、指导数据库详细设计，并为中期检查准备可直接讲解和截图的材料。

本轮只建设核心前期文档和 01～10 号 Obsidian Canvas，不创建应用工程、数据库实例或业务代码。

## 3. 明确延期内容

本轮不创建以下内容：

- 11～15 号后期 Canvas；
- 开发规范、关键代码说明和开发日志；
- 完整测试用例、接口测试、前端测试和 Bug 记录；
- 中期检查清单与软件验收清单；
- 课程报告章节骨架；
- 答辩讲稿、常见问答和演示截图清单；
- 需求变更记录、技术决策记录、会议记录和工作量记录；
- Spring Boot、Vue、MySQL 或其他业务实现。

这些内容将在核心需求和数据库设计确认后分批补充。

## 4. 内容边界

系统仅围绕四类操作展开：气象数据筛选查询、温度与降水可视化、查询结果表格展示、四类基础数据管理。山东地图属于增强功能，不进入核心验收承诺。

课程设计只保留 `T2M` 和 `PRECIP` 两个核心要素，以及 `ECMWF`、`NOAA` 两个示例模型。TDengine、ERA5、NetCDF 在线解析、RMSE、登录权限、微服务和生产部署只作为扩展方向提及，不进入本轮设计或实现承诺。

## 5. 数据库设计原则

数据库固定为 `city`、`forecast_model`、`weather_element`、`forecast_record` 四张核心表。文档明确：

- 每张表的主键、字段类型、非空和唯一约束；
- `forecast_record` 到三张基础表的外键；
- 业务边界检查及 MySQL 8 的 `CHECK` 约束建议；
- 实体完整性和参照完整性；
- 服务于核心组合查询的索引；
- 四张表符合第三范式的依据。

## 6. Obsidian 组织规则

- 文档放在当前 Vault 的 `课程设计/` 目录下。
- Markdown 使用带目录和显示名的内部链接，例如 `[[01-立项与需求/03-需求分析|需求分析]]`。
- 每份核心文档至少链接一个上游依据和一个相关成果，避免孤立笔记。
- `项目导航.md` 作为唯一总入口，链接本轮全部交付物。
- Canvas 的相关说明文档反向链接到对应白板。

## 7. 验证与完成标准

本轮完成时应满足：

1. 25 份核心 Markdown 文档均存在且包含实质内容；
2. 10 份 Canvas 均可通过 JSON 解析；
3. 每份 Canvas 的节点 ID 与边 ID 均不重复；
4. Canvas 节点之间不存在明显重叠；
5. 所有 Markdown 内部链接均能解析到现有文档或 Canvas；
6. 文档没有宣称尚未完成的功能已经实现；
7. 系统范围保持在两人、两周可完成的规模；
8. 导航页可以进入需求、设计、数据库和项目计划资料；
9. 本轮结束状态明确为“等待需求冻结与数据库详细设计”。
