# 第一部分 正式中期检查报告

## 1 课题背景与目标

本课题围绕山东省城市预报资料的查询、可视化与维护，建设一个能够说明数据来源、查询条件和展示结果之间关系的课程系统。用户可以先看全省分布，再查看某城市的变化趋势和双模型数值，最后在管理页面维护基础资料与预报记录。项目的直接目标是完成数据库设计、后端接口、前端交互和测试验证的工程闭环，不是训练或运行新的气象预报模型。[S01][S02]

需求中唯一参与者为“用户”，同时具有查看与维护入口，未划分登录账号和管理员角色。当前实际使用场景是课程展示、教师检查和开发者验证，不应据此推定具备公众天气服务所需的时效性、服务保障或权限控制。两人、约两周是项目安排；成员 A/B 的文件只记载计划主责，不能直接认定为两位实际成员各自完成的工作量。[S02][S03]

可核实的软件成果已超过中检最低演示范围：四页面及十九个业务接口已实现，v1.0 有完整后端打包和前端测试证据，另有本机离线包验证记录。原日程为 9 月 11 日中检、9 月 18 日软件验收、9 月 25 日材料提交；这些是安排日期，本文不把软件收口代写为教师已经检查通过。[S01][S04]

## 2 需求范围与业务边界

| 页面 | 用户要完成的工作 | 主要数据入口 |
| --- | --- | --- |
| /weather | 查看山东 16 市空间分布，切换模型、要素、时次并查看城市详情 | workbench |
| /analysis | 查询一个城市、一个模型的温度和降水变化及四项统计 | trend |
| /comparison | 查询一个城市、一个要素的 ECMWF 与 NOAA 序列 | comparison |
| /management | 维护城市、模型、要素、预报记录四类资源 | 四资源 CRUD |

演示数据明确为合成数据，覆盖 16 城市、2 模型、2 要素、3 个时次，共 192 条预报记录。默认日期为 2026-09-07，时次为 08:00、11:00、14:00。ECMWF 和 NOAA 在本项目中是模型字典标识，并非已经接通的官方数据源；早期七天、3584 条的数字是计划规模，不是当前数据库事实。[S05][S06]

核心流程是“筛选并查询→后端按关系取数→地图或图表呈现→管理临时数据→重新进入展示页查询”。系统没有实时采集、模型训练、误差评分、登录权限、导入导出、批量操作或高级分页筛选。缺测保留缺失语义，真实零降水保留零值。这些边界既约束实现，也约束答辩时可作出的结论。[S01][S07]

## 3 总体架构与技术职责

系统采用单仓库、前后端分目录、Spring Boot 单体分层。浏览器经 Axios 发送 HTTP/JSON 请求；Controller 接收参数，Service 校验规则并组织结果，Mapper 使用 MyBatis-Plus 或 XML 查询 MySQL，再把查询 VO 返回页面。前端不直连数据库，Controller 不直接承担关联查询与统计。[S08][S09]

| 层或工具 | 当前实际配置 | 在本项目中的职责 |
| --- | --- | --- |
| 页面 | Vue 3.5.30、Vue Router 4.6.4 | 四页面路由、响应式状态和组件生命周期 |
| 控件与图形 | Element Plus 2.13.3、ECharts 6.0.0 | 筛选、表格、弹窗、地图、折线与柱状图 |
| 通信与前端构建 | Axios 1.13.6、Vite 7.3.1 | 统一请求、开发代理、静态资源构建 |
| 服务端 | Java 17、Spring Boot 2.7.18 | 请求处理、业务校验、事务、异常响应 |
| 数据访问 | MyBatis-Plus 3.5.7、MyBatis XML | 基础 CRUD；三类展示查询的 JOIN 和排序 |
| 数据库与构建 | MySQL 8；Maven 3.9.16 | 关系约束、精确数值、JAR 打包 |
| 自动测试 | Node test、Vitest、Vue Test Utils；JUnit 5、Spring Boot Test | 工具、组件、Service、Controller、Mapper 和集成验证 |

以上版本来自依赖声明；MySQL 本机与演示包记录为 8.0.46，Java 运行记录为 17.0.11。声明版本并不表示本轮重新安装或测量过所有运行环境。JUnit 等由现有依赖管理提供，不另填材料未记录的版本。[S04][S08][S28]

从现有实现看，可解释的权衡是：Vue 适合筛选、图表和弹窗的联动，ECharts 承担通用绘图，MyBatis-Plus 减少单表 CRUD 重复代码，XML 保留多表查询的可读性。单体和四表范围便于在课程周期内完成联调。这是对代码结构的解释，不是声称团队做过不同框架的量化选型实验。

后端共有五个业务 Controller、五个 Service、四个 Mapper；ForecastRecordMapper 同时支持管理记录和三类展示查询，没有复制三套记录访问层。写请求使用专用 DTO，预报记录与三类展示查询使用 VO；三个字典查询实际直接返回对应 Entity，不能说所有查询都有独立 VO。Entity 对应存储结构，但不直接作为用户写入请求体。[S09][S10]

开发时 Vite 代理 /api 到后端；离线包构建时通过 Maven portable profile 把前端产物纳入 JAR 的 static 目录，实现页面与接口同源。四个页面直接访问和刷新由白名单回退处理，不存在的 API、静态文件及未知页面仍返回 404。开发组织方式与最终部署形式并不矛盾。[S27][S28]

## 4 数据库与接口设计

### 4.1 四表及约束

| 表 | 保存内容 | 主要关系与约束 |
| --- | --- | --- |
| city | 城市编码、名称、经纬度 | 自增 id；city_code 唯一；坐标范围约束 |
| forecast_model | 模型编码、名称、可空描述 | 自增 id；model_code 唯一 |
| weather_element | 要素编码、名称、单位 | 自增 id；element_code 唯一 |
| forecast_record | 城市、模型、要素、预报时间、数值 | 自增 id；三个外键；四字段业务唯一 |

每条记录通过 city_id、model_id、element_id 引用三张字典表。业务唯一键为 (city_id, model_id, element_id, forecast_time)，用于防止同一业务点重复存储；id 则用于稳定地更新、删除某一行。被引用字典不级联删除，数据库外键与 Service 引用检查共同保护关系。[S05][S11]

原理说明：按当前业务依赖，记录键决定 value，城市编码决定城市属性，模型编码决定模型属性，要素编码决定名称和单位。名称等没有重复放入每条预报记录，减少更新异常。字段是单值，字典属性放在各自关系中；在这些依赖成立的前提下，可解释其第一至第三范式设计，而不能只凭“有自增主键”认定规范化。[S05][S12]

预报值使用 DECIMAL(10,2)，经度、纬度使用 DECIMAL(10,6)，后端使用 BigDecimal。时间使用 DATETIME 与 LocalDateTime，接口传 yyyy-MM-dd HH:mm:ss 本地业务时间，不任意转 UTC。数值精度、范围和 PRECIP 非负在后端校验；PRECIP 跨表语义不能简单说成单表 CHECK 已完成全部保障。[S05][S13]

记录表除主键外保留三个二级索引：四字段业务唯一索引；(model_id, element_id, forecast_time) 工作台索引；element_id 单列索引。前两项分别覆盖 city_id、model_id 的左前缀，第三项服务要素引用检查。索引能提供候选路径，不保证所有实际查询都选它或免排序。既有小样本 EXPLAIN 记录曾选 element_id；192 条不足以证明大规模性能。[S05][S14]

### 4.2 十九个业务接口的源码口径

| 路径组 | 方法与计数 |
| --- | --- |
| /api/cities、/api/forecast-models、/api/weather-elements、/api/forecast-records | 每组 GET、POST；/{id} 上 PUT、DELETE，共 4×4=16 |
| /api/weather/workbench | GET，模型、要素、起止时间，共 1 |
| /api/weather/trend | GET，城市、模型、起止时间，共 1 |
| /api/weather/comparison | GET，城市、要素、起止时间，共 1 |

以上按 Controller 映射核对为 19 个业务 API。/api/health 是辅助接口，不计入；页面回退也不计入。管理记录 GET 全量返回、id 升序，没有分页和筛选。响应沿用 code/message/data；400 表示非法输入，404 表示关联或对象不存在，409 表示唯一或引用冲突，未知错误为 500，合法查询无数据为 200。[S07][S09][S15]

## 5 已完成的四个页面

### 5.1 山东气象工作台

/weather 默认 ECMWF 与 T2M。页面加载字典后按核心编码筛选山东 16 市、两模型和两要素；地图把城市编码关联到静态 GeoJSON，不把数组顺序或自增 ID 当作行政区标识。资源来自 China-GeoData，仓库附 MIT 来源说明，仅用于课程示意，不用于测绘。[S16][S17]

Workbench 一次返回所选范围内全省记录，默认响应为 3 个时次、48 条记录。时间轴在本地过滤，切换 08/11/14 不新增 Workbench 请求；相同键在页面实例内可复用缓存，离页时清理并拒绝旧响应。真实浏览器记录包括地图 16/16 匹配、济南详情、模型及要素切换、单位同步和本地时间轴。[S04][S18]

### 5.2 趋势分析

/analysis 默认济南与 ECMWF，温度折线、降水柱状图各处理自己的时间序列，不按数组下标强制对应。初始化自动查询一次，后续修改条件需点击查询。四张统计卡读取后端 max、min、avg、total；null 显示 --，0 不被当成空值。[S19][S20]

济南温度为 19.00、20.20、21.10℃，对应最高 21.10、最低 19.00、平均 20.10℃；降水为 0.00、0.40、0.20 mm，累计 0.60 mm。累计含义依赖数据字典约定的非重叠时段量，不能把未知累计产品直接相加。用户人工记录确认城市、模型切换、Empty、错误恢复、竞态与两档分辨率通过。[S06][S20]

### 5.3 模型对比

/comparison 默认济南与 T2M，固定比较 ECMWF、NOAA，两种要素均为双折线。后端按 model_code 解析真实模型 ID，各自返回按时间升序的值；前端取时间并集升序对齐，缺点映射 null，真实 0.00 保留，不增加误差评分。[S21][S22]

济南 NOAA 温度为 18.40、19.60、20.50℃，降水为 0.10、0.60、0.30 mm。上述数字用于验证取数和绘图，不能据此判断哪个模型更准确。双模型切换要素、城市、错误重试、响应竞态及 /weather、/analysis 回归证据记录在对应归档。[S06][S22]

### 5.4 数据管理

/management 的四个 Tab 各有列表、新增、编辑、删除。写表单使用独立草稿，保存期间防止重复提交；唯一与引用冲突保留草稿和原列表，写入成功但刷新失败单独提示，不诱导重复写入。字典变更使记录显示元数据和下拉依赖失效，在下次使用前刷新。[S23][S24]

既有真实验收包括四资源 CRUD、模型描述清空、PRECIP 零值与负值、重复业务键，以及临时要素被引用时删除、改编码、改单位返回 409。临时记录 #202、要素 #8 已按先记录后字典清理。宽屏及错误状态同时包含实际操作、用户确认与模拟证据，不能全部笼统称作真实 MySQL 验收。[S25]

## 6 实际问题与处理过程

### 6.1 管理扩展字典影响固定范围工作台

现象：最终审查发现，工作台直接使用全量字典时，管理新增临时城市会破坏严格的 16 市映射，临时模型和要素也会进入不支持的选项。原因是管理全量字典与展示核心范围没有在页面边界分开。处理是在 workbenchState 中先按核心编码过滤，再做完整性校验，管理接口仍全量返回。三类临时字典测试先失败后通过，另补缺核心城市不能被临时城市替代的用例；前端由 142 增至 146 项。本项边界修复是自动测试证据，不冒充新增临时字典后的再次真实写库浏览器验收。[S04][S17]

### 6.2 MySQL 连接公钥获取受限

现象：真实运行出现 Public Key Retrieval is not allowed，接口无法正常取数。记录中的处理是在原有 useSSL=false 的 JDBC URL 后追加 allowPublicKeyRetrieval=true，保留环境变量机制，不修改账号、密码、Schema 或 Seed。修复后城市、模型、要素接口均返回 200，三展示页恢复。此设置服务本地演示，不能作为公网数据库通信的安全方案；不能声称修复了全部数据库安全风险。[S22]

### 6.3 Windows 中文路径导致演示数据库启动失败

现象：离线包在含中文和空格的解压目录中经历初始化或启动失败。运行记录定位到 MySQL INI 编码和 Windows 重启监控器的多字节路径处理。处理采用系统 ANSI 编码并检查往返一致性，同时使用 --no-monitor；失败目录保留，不自动清空重试。最终 test 7 在本机中文/空格目录完成首次初始化、启停和数据持久化。只在本机 CP936 验证，不能覆盖所有系统代码页，无法表示的路径应改为简短英文目录。[S28][S29]

### 6.4 初始化过程中停止可能过早报告成功

现象：离线包独立审查指出启动与停止存在生命周期竞态，初始化尚未结束时不能只根据某一进程观察宣布停止完成。处理加入共享生命周期锁及初始化退出未确认标记，只有确认退出后才能推进状态；身份核验失败或超时不广泛结束进程。真实 test 7 在完成标记出现前触发停止，等待后确认进程和监听退出；“初始化无法确认退出”的超时分支使用 fixture 验证，并非人为挂起真实数据库后的实测。启动后意外退出仍主要依赖日志排障，没有自动故障恢复。[S28][S29]

这些问题分别暴露了页面数据范围、连接配置和部署生命周期的边界。所采用的修复都围绕既有功能，不以增加业务模块解决问题，也不以一次通过代替换机验证。

## B 技术架构

### Q06 为什么前后端分离 演示时又放进一个 JAR

30 秒回答：前后端分离主要是源码、职责和接口边界分开。开发时 Vue 用 Vite，后端独立运行；演示时把已构建静态文件纳入 Spring Boot JAR，同源提供页面和 API。部署合并没有取消分层，也不需要在目标电脑启动 Node。

证据：[S08][S27]。边界：以下是从现有实现看可解释的权衡，不是已记录的框架选型实验。

一分钟追问：开发代理把 /api 转给后端，便于调试；portable profile 仅改变资源装配方式，不改变十九个业务接口。Vue Router 的历史路由需要服务器在直接刷新时返回入口页，所以后端只对白名单四页面回退。缺失 API 或脚本必须保留 404，若全部回退为 HTML，会把资源错误伪装成成功。PortableWebTests 和发布包记录验证了这些边界。运行时只需要随包 Java 和独立 MySQL，Maven/Vite 是构建工具。

### Q07 各技术具体负责什么

30 秒回答：Vue 管页面状态，Element Plus 管表单表格，ECharts 绘图，Axios 发统一请求，Spring Boot 处理 HTTP 和应用生命周期，Service 执行业务规则，MyBatis-Plus 做基础 CRUD、XML 写关联查询，MySQL 保证关系存储与约束。

证据：[S08][S09][S17][S19][S21][S23]。边界：没有 Redis、JWT、Spring Security 或 GIS 服务，不把依赖清单以外的技术补进答辩。

### Q08 为什么分 Controller Service Mapper

30 秒回答：Controller 负责参数和 HTTP 入口，Service 负责关联校验、规则、事务与结果组织，Mapper 负责 SQL。这样 HTTP 状态、业务计算和数据访问可以分别测试；三个展示查询复用一个 ForecastRecordMapper，不复制记录数据层。

证据：[S09][S10][S15][S26]。边界：分层减少职责混杂，不自动保证零缺陷或高性能。

一分钟追问：以 Trend 为例，Controller 接收城市、模型和起止时间并严格解析日期；Service 检查时间范围和字典，按编码取得 T2M/PRECIP 的 ID；XML 联表查询并排序；Service 分开整理两序列和统计，返回 TrendVO。本项目展示 Controller 测试使用真实 Controller 与 Service、模拟 Mapper 验证 HTTP 行为；Service 测试模拟 Mapper 验证均值，真实集成测试再验证 SQL。不能把 Mock 成功误认为数据库也成功。

### Q09 DTO Entity VO 为什么不是同一种对象

30 秒回答：DTO 定义用户可以写的字段及校验，Entity 对应四张存储表，VO 定义页面需要看到的结果。预报记录写请求传关联 ID、时间和值，查询 VO 还可以带城市名、模型名和单位，但这些名称不因此重复存进记录表。

证据：[S10][S11]。边界：三个字典查询实际直接返回 Entity，独立 VO 用于记录和展示查询；使用 DTO 不是权限系统。

### Q10 一个点击怎样从页面到数据库再回来

30 秒回答：以对比页“查询”为例，页面读取草稿筛选条件，经已有 Axios 请求 comparison；Controller 校验参数，Service 查城市、要素并按编码取得两模型，Mapper XML 读记录，返回 ComparisonVO。前端校验响应后按时间并集对齐，两条线使用同一时间轴。

证据：[S09][S21]。边界：requestVersion 只让最新请求更新页面，不等于取消数据库已收到的查询。

## C 数据库设计

### Q11 为什么拆四张表 不放一张大表

30 秒回答：城市、模型、要素是复用的字典，一条预报记录引用三者并保存时间和值。若每行都存城市坐标、模型描述和要素单位，同一属性会重复出现，改名时容易漏改。查询通过关联取名称，写入由外键保证引用存在。

证据：[S05][S11][S12]。边界：这是依据当前业务依赖作的规范化解释，不是说表拆得越多越好。

一分钟追问：在当前样例中，同一城市会出现在两个模型、两个要素和三个时次的多条记录里。假如城市名称放进每一条记录，改名称要同时改多行；没有预报记录时也难以单独维护城市。拆成 city 后，一次改名即可由后续查询读取新名称，forecast_record 不需要批量改冗余字段。反过来，删除城市可能让记录失去含义，所以先拒绝被引用字典删除，而不是直接级联清空历史记录。

### Q12 如何用实际字段解释第一第二第三范式

30 秒回答：原理说明：第一范式要求字段是单值，当前每行是一条城市、模型、要素、时间组合；第二范式强调非键属性依赖完整候选键，value 对应完整业务组合；第三范式避免非键属性经其他非键属性传递依赖，城市名和单位放在字典表而不冗余在记录里。

证据：[S05][S12]。边界：范式判断依赖业务函数依赖，不能仅看有 id 就下结论。

一分钟追问：当前依赖可以写成“城市编码决定城市名与坐标”“模型编码决定模型名与描述”“要素编码决定要素名与单位”“完整记录业务键决定数值”。如果把 cityName 放在记录表，记录业务键先确定 cityId，cityId 再决定名称，造成冗余和更新异常。四表设计把这些属性归回字典。若未来允许同一城市多套行政版本或多起报批次，依赖可能改变，需要重新分析；不能把当前 3NF 结论无条件套用到未来模型。

### Q13 自增主键与四字段业务唯一键有何区别

30 秒回答：自增 id 标识一条物理记录，便于 /{id} 更新和删除；四字段业务键表达“同城市、同模型、同要素、同预报时刻不能重复”。即使两个行 id 不同，也可能重复表达同一业务点，因此两种约束都需要。

证据：[S05][S11]。边界：当前没有预报起报批次字段，未来多批次不能直接沿用这一唯一性假设。

一分钟追问：例如济南、ECMWF、T2M、2026-09-07 08:00 已有一条记录，再插入相同组合应返回 409，而不是给新 id 就算合法。修改原记录时，Service 判重需要排除自己的 id，否则会把未变的业务键误判为冲突。Service 提供友好提示，数据库 UNIQUE 负责最后兜底。删除后 id 出现间隔是正常现象，不能为了连续编号去重排主键或修改关联。

### Q14 外键和引用保护有什么区别

30 秒回答：外键确保记录关联的字典存在，并阻止违规删除；Service 可以先检查引用，返回明确 409，并保护已引用编码和要素单位不被改变。名称等展示字段按契约仍可修改。只有外键并不能阻止改单位导致原数值解释改变。

证据：[S05][S11][S25]。边界：没有级联删除或逻辑删除，当前规则也不等于保存了字典全部历史版本。

### Q15 索引列顺序与最左前缀怎样解释

30 秒回答：原理说明：联合索引按列序组织，通常从最左侧连续条件开始利用。工作台按模型、要素等值加时间范围查询，因此设计了相应三列索引。业务唯一索引从城市开始，适合城市相关查询；不能跳过中间列却声称后面时间一定连续命中。

证据：[S05][S14]。边界：已有小样本执行计划不支持“所有查询必用联合索引”或“一定免排序”。

一分钟追问：唯一索引是 city_id、model_id、element_id、forecast_time。Trend 有城市和模型条件，可从前缀理解，但同时查两要素要结合实际计划；Comparison 条件包含城市和要素，也不能把未单一限定的模型列忽略。Workbench 另建模型、要素、时间索引，避免只能从城市前缀访问。记录还保留 element_id 单列用于引用关系。优化器会看样本量、选择性和统计信息，DB 阶段小样本曾选 element_id；没有当前负载的 EXPLAIN 就不承诺具体 key 或 rows。

### Q16 192 条数据能说明性能好吗

30 秒回答：不能。192 条能核对组合、排序、空值和图表，但查询延迟与大数据量时的行为不同。现有材料没有吞吐量、P95 延迟、并发压测或容量上限。管理全量列表尤其需要在扩大数据时重新评估。

证据：[S04][S06][S14]。边界：分页、负载测试和索引调整是未来候选，不是已经完成的性能优化。

### Q17 为什么用 DECIMAL 和 BigDecimal

30 秒回答：预报值需要两位小数，数据库用 DECIMAL(10,2)，Java 用 BigDecimal，便于保持十进制精度。平均温度明确按 HALF_UP 保留两位，不让二进制浮点近似决定舍入。前端显示精度不代替后端存储边界校验。

证据：[S05][S13][S20]。边界：DECIMAL 只解决规定范围内数值表示，不保证采集数据准确；超范围或超精度仍需拒绝。

### Q18 DATETIME 与 LocalDateTime 如何配合

30 秒回答：接口使用 yyyy-MM-dd HH:mm:ss，本项目把它解释为本地业务时间；后端严格解析为 LocalDateTime，数据库存 DATETIME。前端日期控件保留这个口径，不随意转 ISO UTC。非法日期、格式或倒置范围应返回 400，起止相等可以表示一个时刻。

证据：[S13][S15][S19]。边界：LocalDateTime 本身没有时区信息，真实跨时区数据接入必须重新明确时区和转换规则。

## D 气象查询与计算

### Q19 三个查询的参数为什么不同

30 秒回答：Workbench 取全省，传模型、要素和时间；Trend 固定双要素，传城市、模型和时间；Comparison 固定双模型，传城市、要素和时间。接口围绕各页面一次需要的数据设计，减少前端拼接不同响应造成的不一致。

证据：[S07][S09]。边界：它们是三种查询组织方式，不是三个独立预测算法。

### Q20 地图如何关联城市 短名与全名怎么处理

30 秒回答：代码用核心城市编码找到字典城市，再关联 GeoJSON 的行政区属性，显式处理“济南”和“济南市”等显示名差异。映射需核对 16 市完整性，不能依赖数组顺序。图上没有记录时应保持地理轮廓和缺测语义。

证据：[S16][S17][S18]。边界：静态 GeoJSON 用于课程示意，没有测绘资质或完整 GIS 能力。

一分钟追问：城市自增 ID 由数据库分配，不是行政编码，也不能保证不同实例一致。页面先按 JINAN 等代码取得当前城市对象，再建立城市 ID 与地图区域名称的映射；GeoJSON 区域名用于 ECharts 数据项名称，接口的 cityId 用于查数。临时城市不能补上缺少的核心济南，严格映射应报缺项。地图许可说明记录了来源和 MIT 许可，保留原资源并随离线包携带，不需要运行时联网下载地图。

### Q21 默认项为什么不用 ID 临时字典为何不能污染工作台

30 秒回答：默认济南、ECMWF、T2M 是业务含义，应通过编码解析当前真实 ID。管理字典是全量的，允许临时资源；工作台只支持冻结的核心范围，所以先过滤核心编码再校验。这样新增临时数据不会变成不支持的展示选项。

证据：[S17][S04]。边界：工作台缺任一核心城市会报错；缺默认模型或要素但仍有其他可用核心选项时，会回退并警告，无可用选项时才报错。过滤不会自动修复字典。

### Q22 两模型时间不一致如何对齐

30 秒回答：后端各模型独立按时间升序返回，不补点；对比页取两个序列时间的并集并排序，再按时间查每个模型的值。缺少的点是 null，不能用相同数组下标强行对应，更不能填 0。两种要素都按这套规则绘制双折线。

证据：[S21][S22]。边界：两模型都缺失的时刻不会凭空加入并集；趋势页也不会自动插入缺失时刻。因此不能统称“任何缺测都自动断线”。不进行插值、补测或准确率计算。

### Q23 缺测与真实零如何区分

30 秒回答：零降水表示这条数据的量确实为零，缺测表示没有该数据，两者含义相反。后端不凭空补零；对比页对齐时用 null 表示缺点，统计空值显示 --，但数值 0 仍正常显示。趋势两系列也保持独立。

证据：[S06][S19][S21]。边界：浏览器模拟空响应验证的是界面处理，不说明真实数据库被清空。

一分钟追问：济南 ECMWF 的第一条降水正是 0.00。如果使用 value || '--' 这样的真假判断，就会误把零显示为空；应判断 null/undefined 或约定的缺值。两模型时刻不齐时填零会制造假的骤降，所以 Comparison 采用时间映射，缺点保留 null。没有任何温度记录时 max/min/avg 都应为 null，而不是零度；没有降水记录时 total 也为 null，不能把“没记录”解释成“没有下雨”。

### Q24 四项统计在哪里计算 怎样核对

30 秒回答：在 WeatherQueryService 中计算，前端只读取 statistics。济南温度 19.00、20.20、21.10 对应 max 21.10、min 19.00、avg 20.10；降水 0.00、0.40、0.20 对应 total 0.60。温度均值用 BigDecimal HALF_UP 两位。

证据：[S06][S20]。边界：前端不另算一套统计，避免与后端口径不同；当前统计基于实际返回的已有点，不意味着完整观测覆盖。

### Q25 降水值能直接求和吗

30 秒回答：只有时间段语义允许时才可以。本项目约定 PRECIP 为非重叠三小时时段量，所以对选中记录求和。若真实产品给的是自起报开始的累计值，直接相加会重复计量，需要先按产品规则转换。

证据：[S06][S20]。边界：按冻结定义，每点对应结束于该时刻的前三小时，08/11/14 三点对应 05—14 的三个时段，不是“六小时累计”。CRUD 未强制三小时间隔或校验区间重叠，当前没有真实产品转换链路。

### Q26 两模型差异能说明谁更准吗

30 秒回答：不能。对比页只呈现同一城市、要素下两模型数值，不含观测真值，且当前数据为合成样例。曲线接近或更平滑并不代表更准确；项目没有 RMSE、MAE、Bias、Accuracy 或评分。

证据：[S21][S22]。边界：未来评估须明确观测、空间匹配、预报时效和评估样本，不能把视觉差异直接称作预测误差。

## E CRUD 与一致性

### Q27 前端校验了 后端还要校验什么

30 秒回答：前端校验让用户及时纠错，但请求可以绕过页面，后端仍要检查必填、长度、经纬度、数值精度、严格日期、ID、关联存在和 PRECIP 非负。0.00 合法，模型 description 可以清空为 null。数据库再兜底唯一和外键。

证据：[S10][S13][S15]。边界：这些是输入和数据完整性保护，不等于身份认证或完整安全审计。

### Q28 400 404 409 500 分别怎么用

30 秒回答：非法格式和规则输入为 400；指定对象或关联不存在为 404；重复编码、重复业务键或被引用限制为 409；无法预期的内部错误为 500。合法查询无匹配记录是 200，不能因为数组为空就报 404。

证据：[S15][S07]。边界：网络被浏览器阻止不是后端返回了 500，应区分根本没有响应与 HTTP 错误响应。

### Q29 已经在 Service 判重 为什么还要 UNIQUE

30 秒回答：原理说明：两个并发请求可能都在插入前查到“不存在”，只靠 Service 判重会有竞态。数据库 UNIQUE 才能在最终写入时阻止重复，异常再映射 409。更新时判重需排除当前 id，不能把自己算作重复记录。

证据：[S05][S11][S15][S26]。边界：有兜底约束不等于经过高并发性能验证。

一分钟追问：Service 查询是为了尽早给出可理解的冲突原因，但“查询通过”和“写入完成”之间存在时间窗口。数据库的唯一索引约束保证第二个相同业务键不能静默落库，事务失败会回滚本次数据库写入。当前业务唯一键四列明确，字典各自编码也有唯一键。预报记录更新同时要检查新关联是否存在和要素是否允许该值；不能为了消除重复错误而先删旧数据或覆盖已有记录。

### Q30 被引用字典哪些能改 哪些不能改

30 秒回答：已被记录引用时，城市编码、模型编码、要素编码及要素单位受保护，修改会返回 409；这些字段改变可能使原数值业务解释变化。展示名称、描述等按契约允许更新，删除被引用字典也拒绝，不级联删除记录。

证据：[S11][S25]。边界：单位冲突当前复用编码冲突提示，是已记录的非阻塞文案问题，不能说提示已经完全精细化。

### Q31 事务与行锁保护了什么竞态

30 秒回答：写操作在事务内，Service 读取有关字典时使用锁定查询，把“检查引用或含义”和“记录写入”协调起来。字典修改删除与新建引用记录需要争用相应字典锁，避免刚检查完未引用就被另一条写入改变事实；数据库外键、唯一约束仍兜底。

证据：[S11][S26]。边界：实际按 city→model→element 加锁，测试检查了锁查询调用；未验证真实双连接竞争。没有版本号防止旧表单覆盖新值，也不承诺绝无死锁。管理记录 GET 使用只读 REPEATABLE_READ 批量组装快照，不能推广为所有展示查询均在同一事务快照。

### Q32 回滚保证什么 HTTP 写入也自动回滚吗

30 秒回答：事务可以在异常时撤销该事务内数据库修改，集成测试的事务回滚可避免留下测试记录。浏览器调用成功的 HTTP 写入通常已经提交，不会因测试结束自动撤销，必须删除临时记录、再删除临时字典。

证据：[S26][S25][S28]。边界：回滚不能撤销浏览器已经显示的消息、外部副作用或自增序列所有变化；不能保证 ID 连续。

### Q33 description 清空 非法 ID 日期怎样处理

30 秒回答：模型描述允许 null，清空后读取显示 --，更新必须确实把 null 写入而不是被更新策略忽略。ID 拒绝非法形式和不安全数值；日期严格按本地业务格式解析，非法 JSON、日期或倒置时间返回 400，而不是自动纠正后写库。

证据：[S10][S13][S15][S25]。边界：显示 -- 只代表没有描述或统计，不能把它作为实际字段值存入数据库。

## F 前端状态

### Q34 编辑为什么复制 Draft 怎样防重复提交

30 秒回答：直接绑定列表对象会让用户尚未保存的修改提前显示到表格，所以编辑用独立草稿，取消即可丢弃。保存期间有提交状态和按钮限制，避免连续点击；遇到 409 保留草稿，让用户修正而不是清空输入。

证据：[S23][S24][S25]。边界：前端按钮限制不能替代后端幂等性或唯一约束，直接发送重复请求仍由后端处理。

### Q35 如何防止旧响应覆盖新响应

30 秒回答：状态模块使用递增请求版本，发送时记下版本，响应回来只有仍是当前版本且页面有效才更新。快速查询时先发的请求即使最后返回，也不能覆盖最后一次查询。组件卸载后同样忽略旧响应。

证据：[S17][S19][S21][S23]。边界：这是 UI 竞态保护，不是网络取消，也不证明服务端请求没有执行。

### Q36 写成功刷新失败 为什么不能提示保存失败

30 秒回答：写请求已经成功，后续 GET 失败只表示列表未刷新。若提示保存失败，用户可能重复提交，造成重复冲突。当前状态把写结果和刷新分开，提示已保存但需要重试刷新，保留可恢复的列表状态。

证据：[S23][S24]。边界：不能因为列表还旧就推定数据库没更新，应核对写响应与随后的读取结果。

### Q37 字典更新后下拉和缓存怎么刷新

30 秒回答：管理模块在字典写成功后让记录元数据与依赖字典失效，下次使用前重新加载。Workbench 缓存属于页面实例，离开清理，重新进入取新字典和记录；Trend、Comparison 不使用结果缓存。四页不是同一个缓存策略。

证据：[S17][S19][S21][S23]。边界：没有跨浏览器推送；其他客户端改库后，当前页面可能需要重新查询或重载。

### Q38 Loading Empty Error Retry 和图表生命周期怎么处理

30 秒回答：Loading 表示正在取数且框架保留；Empty 是合法空结果；Error 表示请求或依赖失败；Retry 用当前条件恢复。图表容器变化时 resize，离页时 dispose 并移除监听，避免旧实例继续处理事件。

证据：[S19][S21][S23][S25]。边界：管理 Empty 是受控浏览器模拟；正常 Console 无错误的验收记录不代表所有设备都不会出错。

证据：[S04][S26]。边界：用户完整 package 的 293 项成功是历史实机证据，不冒充本文生成时重新执行。

证据：[S25][S28]。边界：数量 16/2/2/192 相同不证明所有种子字段逐值未变，HTTP 写入也不享有测试事务自动回滚。

证据：[S29][S30]。边界：本地私有配置不是加密保险库，具有本机高权限的人仍是信任边界；本文不展示任何密码。

## 一页速查

一句话：本系统用四表和十九个业务接口，把山东城市合成预报资料组织成地图、趋势、模型对比和维护四个页面，验证数据到界面的完整流程。

核心架构：Vue／Axios → Controller → Service → MyBatis-Plus／XML → MySQL；查询 VO 返回页面。开发前后端分开，离线包静态资源与 API 合并进 JAR。[S08][S09][S27]

四表关系：city、forecast_model、weather_element 为字典，forecast_record 用三个外键引用；id 是行标识，四字段唯一键控制业务重复。[S05]

四页面：/weather 看 16 市分布和时次；/analysis 看 T2M 折线、PRECIP 柱状与统计；/comparison 两要素均双折线；/management 四资源 CRUD、无分页。[S04]

演示样例：济南 ECMWF，2026-09-07 08/11/14；温度 19.00／20.20／21.10℃，降水 0.00／0.40／0.20 mm；四统计 21.10／19.00／20.10／0.60。NOAA 温度 18.40／19.60／20.50，降水 0.10／0.60／0.30。[S06]

三个真实难点：临时字典混入核心展示范围；MySQL 公钥获取配置；Windows 中文路径与启停生命周期。分别用核心编码过滤、最小 JDBC 修复、编码检查与生命周期锁处理。[S04][S22][S28]

三个限制：合成样例不证明预报准确性；没有认证和生产运维保障；目标笔记本与物理断网未验证。大包体积等已知非阻塞项不掩盖。[S04][S28]

最容易说错：十九个是业务 API，不含 health；缺测不等于零；模型差值不等于误差；管理 Empty 是模拟；293 是完整后端基线，284 是 portable 非数据库测试；数量恢复不等于字段全库一致。

## 三分钟汇报稿

老师好，我汇报的课题是《山东省气象预报数据可视化系统的设计与实现》。这个项目的目标是把城市预报资料从数据库查询出来，以地图、时间趋势和模型对比的方式展示，并提供基础维护入口。它处理的是预报数据，不是自己计算天气。当前使用固定的合成课程数据，覆盖山东 16 个城市、两个模型、两个要素和三个时次，共 192 条记录。

系统采用 Vue 前端、Spring Boot 后端和 MySQL。数据库分成城市、模型、要素、预报记录四张表，记录通过外键引用字典，并用城市、模型、要素、预报时间组成业务唯一键。Controller、Service、Mapper 分别负责请求、业务规则和查询。前端修改筛选条件后，后端按页面需要返回结构化结果。

现在四个页面已经完成。工作台一次取得全省数据，时间轴在本地切换；趋势页展示温度折线、降水柱状和四项后端统计；对比页按时间并集展示 ECMWF 与 NOAA，两种要素都是双折线；管理页提供四类资源的新增、修改、删除及冲突提示。我们特别区分了缺测与真实零值，也处理了旧请求覆盖、草稿误改列表和写入成功但刷新失败的问题。

验证方面，归档中的前端是 146 项测试通过，用户本机完整后端打包是 293 项测试无失败、错误或跳过，四页和真实数据库接口有验收记录。管理空列表属于浏览器模拟，不是真实清空数据库；数据清理核对了临时 ID 和数量，但没有夸大全库字段一致性。最终审查还修复了管理临时字典影响工作台固定 16 市范围的问题。

为便于展示，另制作了带 Java 和独立 MySQL 进程的 Windows 离线包，本机启停和重启保留数据已经验证。目标笔记本和真正关闭网络的试演仍待完成。目前没有实时数据、权限系统或性能压测结论，后续重点是完成换机试演与课程材料，真实数据接入需先明确来源和时间语义。我的个人分工和具体贡献将在正式汇报前依据实际记录补充。
