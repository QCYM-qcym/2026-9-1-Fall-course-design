# 3NF 规范化分析

## 1. 分析口径

规范化分析以四张关系表的固定字段和函数依赖为依据。所有字段均为原子值；代理主键 `id` 唯一确定本表其余属性。基础实体的编码字段各自构成候选键，预报记录的 `(city_id, model_id, element_id, forecast_time)` 构成候选业务键。

## 2. 城市表 `city`

关系模式为 `city(id, city_code, city_name, longitude, latitude)`。

- 1NF：`city_code`、`city_name`、`longitude`、`latitude` 均保存单一不可再分的值，不含重复组。
- 2NF：主键 `id` 是单字段键，所有非主属性完全依赖 `id`，不存在对复合主键一部分的依赖。
- 3NF：候选键 `city_code` 也能唯一标识城市；`city_name`、`longitude`、`latitude` 描述该城市，不由其他非主属性决定，不存在非主属性间的传递依赖。

因此 `city` 满足 3NF。

## 3. 预报模型表 `forecast_model`

关系模式为 `forecast_model(id, model_code, model_name, description)`。

- 1NF：模型编码、名称和说明均为单值属性。
- 2NF：主键 `id` 是单字段键，`model_code`、`model_name`、`description` 均完全依赖 `id`。
- 3NF：候选键 `model_code` 可唯一标识模型；`model_name` 与 `description` 直接描述模型，不依赖另一个非主属性。

因此 `forecast_model` 满足 3NF；允许为空的 `description` 不改变函数依赖关系。

## 4. 气象要素表 `weather_element`

关系模式为 `weather_element(id, element_code, element_name, unit)`。

- 1NF：要素编码、名称和单位均保存单一值，例如 T2M、2 米气温和 ℃ 分列保存。
- 2NF：主键 `id` 是单字段键，`element_code`、`element_name`、`unit` 均完全依赖 `id`。
- 3NF：候选键 `element_code` 可唯一标识要素；`element_name` 和 `unit` 直接描述该要素，不以其他非主属性为决定因素。

因此 `weather_element` 满足 3NF。

## 5. 预报记录表 `forecast_record`

关系模式为 `forecast_record(id, city_id, model_id, element_id, forecast_time, value)`，候选业务键为 `(city_id, model_id, element_id, forecast_time)`。

- 1NF：三个外键、有效时间和数值均为原子值，一行只表达一个业务组合在一个有效时间的一个预报数值。
- 2NF：以代理主键 `id` 判断时不存在部分依赖；以组合候选键判断时，`value` 依赖四个字段的完整组合，任意缺少城市、模型、要素或有效时间都不能唯一决定该预报值。
- 3NF：除候选键属性外仅有事实值 `value`；`value` 直接依赖候选键，不通过其他非主属性传递决定。三个外键只是引用对应实体，不在本表复制实体描述。

因此 `forecast_record` 满足 3NF。

## 6. 冗余控制与异常规避

`forecast_record` 不保存 `city_name`、`model_name`、`element_name` 或 `unit`。这些属性分别只保存在 `city`、`forecast_model`、`weather_element` 中，查询时通过外键连接取得。这样可避免：

- 修改城市、模型或要素名称时需要批量同步历史预报记录的更新异常；
- 修改要素单位时同一要素出现多个单位版本的不一致；
- 删除最后一条预报记录时意外丢失基础实体信息的删除异常；
- 新建尚无预报记录的基础实体时无法保存资料的插入异常。
