# 完整性约束设计

## 1. 约束目标

完整性约束用于保证四类演示资料可唯一识别、预报记录引用有效、同一业务组合不重复，并在数据库可通用表达的范围内阻止越界数据。数据库约束与业务层校验共同工作，不能由数据库通用约束准确表达的要素差异规则由业务层承担。项目技术栈总称为 MySQL 8，但本页约束的目标实例最低版本为 MySQL 8.0.16+。本页只定义待实现的约束，不表示相关 DDL 已执行。

## 2. 实体完整性

四张表均以非空 `BIGINT UNSIGNED` 字段 `id` 为主键，并使用 `AUTO_INCREMENT` 生成：

- `city.id`
- `forecast_model.id`
- `weather_element.id`
- `forecast_record.id`

主键保证每行具有稳定且唯一的关系标识。业务层不允许修改已生成的主键。

## 3. 参照完整性

| 外键名 | 子表字段 | 引用目标 | 更新策略 | 删除策略 |
| --- | --- | --- | --- | --- |
| `fk_forecast_record_city` | `forecast_record.city_id` | `city(id)` | `ON UPDATE RESTRICT` | `ON DELETE RESTRICT` |
| `fk_forecast_record_model` | `forecast_record.model_id` | `forecast_model(id)` | `ON UPDATE RESTRICT` | `ON DELETE RESTRICT` |
| `fk_forecast_record_element` | `forecast_record.element_id` | `weather_element(id)` | `ON UPDATE RESTRICT` | `ON DELETE RESTRICT` |

三个外键字段均非空，因此每条预报记录必须分别关联一个真实存在的城市、预报模型和气象要素。基础资料已被引用时禁止直接删除；界面应在删除前检查引用并给出提示。基础资料修改必须先通过业务层验证，主键不作为可编辑业务属性。

## 4. 唯一性约束

| 约束名 | 表 | 字段 | 目的 |
| --- | --- | --- | --- |
| `uq_city_city_code` | `city` | `(city_code)` | 防止城市编码重复。 |
| `uq_forecast_model_model_code` | `forecast_model` | `(model_code)` | 防止模型编码重复。 |
| `uq_weather_element_element_code` | `weather_element` | `(element_code)` | 防止要素编码重复。 |
| `uq_forecast_record_business` | `forecast_record` | `(city_id, model_id, element_id, forecast_time)` | 防止同一城市、模型、要素和有效时间出现多条记录。 |

组合唯一约束是新增及修改判重的数据库兜底；修改按记录 id 定位；`forecast_time` 或任一外键都不单独唯一。

## 5. 非空与类型约束

| 表 | 非空字段 | 可空字段 |
| --- | --- | --- |
| `city` | `id`, `city_code`, `city_name`, `longitude`, `latitude` | 无 |
| `forecast_model` | `id`, `model_code`, `model_name` | `description` |
| `weather_element` | `id`, `element_code`, `element_name`, `unit` | 无 |
| `forecast_record` | `id`, `city_id`, `model_id`, `element_id`, `forecast_time`, `value` | 无 |

编码长度统一为 `VARCHAR(32)`，名称长度统一为 `VARCHAR(50)`；经纬度为 `DECIMAL(10,6)`，模型说明为 `VARCHAR(255)`，单位为 `VARCHAR(16)`，有效时间为 `DATETIME`，预报值为 `DECIMAL(10,2)`。

## 6. 数值边界与业务校验

数据库层拟设置两个通用且含义稳定的城市坐标 `CHECK` 约束。MySQL 从 8.0.16 起才创建并执行 `CHECK` 约束；8.0.15 及以下版本只解析但忽略该约束，因此本设计不将这些早期 8.0 版本视为可用的约束执行环境：

- `chk_city_longitude`：`longitude BETWEEN -180 AND 180`。
- `chk_city_latitude`：`latitude BETWEEN -90 AND 90`。

## 7. 写入与删除处理顺序

新增或修改时先检查格式、时间和值（400），再检查目标/关联存在（404），最后检查业务限制和唯一性（409）；单次写事务执行，数据库唯一与外键约束兜底并发冲突。删除引用中的字典返回 409，不级联；不存在返回 404。成功后前端刷新字典/列表并清工作台缓存，重查趋势确认结果。
