# 索引设计 V2

## 1. 最小方案

面向约 3584 条预报记录，优先满足业务唯一性、外键检查和高频工作台查询。以下均为设计，未创建索引或运行 EXPLAIN。MySQL 8.0.16+，沿用四表、字段和约束。

目标“2～3 个必要索引”指 forecast_record 除主键外的二级索引，不是全库连主键/字典唯一键合计。最终采用 3 个二级索引：

| 索引 | 列顺序 | 决策与用途 |
| --- | --- | --- |
| uq_forecast_record_business | city_id, model_id, element_id, forecast_time | 保留唯一索引；业务判重，城市/模型/要素等值后时间范围扫描；city_id 外键左前缀 |
| idx_forecast_record_workbench | model_id, element_id, forecast_time | 新的工作台联合索引，替换旧 model_id 单列；支持 model_id 外键左前缀 |
| idx_forecast_record_element_id | element_id | 保留，element_id 外键/引用检查；前两项均不以 element_id 开头 |

另保留 forecast_record 的 PRIMARY(id)。三个字典表各保留 PRIMARY(id) 和各自编码唯一索引 uq_city_city_code、uq_forecast_model_model_code、uq_weather_element_element_code，不为名称/坐标/单位再建索引。

## 2. 实际查询与左前缀

| 场景 | WHERE / ORDER BY | 当前可用访问路径与限制 |
| --- | --- | --- |
| Workbench | model_id、element_id 等值，时间范围，山东 cityCode 集合；按时间、city_id 排序 | workbench 联合索引前两列等值、末列范围；cityCode 联表过滤；city_id 排序可能 filesort，不声称完全免排序 |
| Trend | city_id、model_id 等值，T2M/PRECIP，时间范围 | 业务唯一索引可用 city_id/model_id 前缀；按两要素 id 条件可能分范围；不能声称跳过 element_id 仍直接时间范围扫描 |
| Comparison | city_id、element_id，ECMWF/NOAA，时间范围 | 唯一索引至少用 city_id 前缀，其他条件过滤或多模型分范围；不声称跳过 model_id 就匹配连续左前缀 |
| 管理查询 | 五参数可选组合，时间成对 | 依实际条件选择上述索引，纯时间/全量管理在小数据集可全扫，不为每种组合建索引 |

完整数据时一个城市约 224 条、一个城市/模型约 112 条；趋势/对比的小范围过滤和排序可以接受。优化器最终选择取决于数据与统计信息，本轮没有执行计划或性能实测。

## 3. 不机械增加候选索引

暂不建立 (city_id,model_id,forecast_time) 与 (city_id,element_id,forecast_time)：它们可能改善特定查询，但当前规模收益不足以抵消额外维护/展示复杂度。保留为后续实测候选，不列入 DDL。

不保留旧 idx_forecast_record_model_id，因为新的联合索引以 model_id 开头；不加 city_id 单列、重复业务键索引、forecast_time 单列、value 或基础名称索引。element_id 单列不能被非左前缀联合索引代替，故保留。

## 4. 后续验证（未运行）

工程阶段以 MySQL 8.0.16+ 检查 SHOW CREATE TABLE、SHOW INDEX，确认未产生重复外键索引；对三个 XML 查询及管理组合执行 EXPLAIN，记录 key、rows、Extra，尤其确认是否 filesort。对约 3584 条初始化数据核对查询结果和排序。只有实测证据证明必要才增删索引，并同步 SQL 文档及脚本。
