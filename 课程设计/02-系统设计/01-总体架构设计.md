# 总体架构设计

## 1. 设计定位

本文将冻结的需求转化为后续页面、数据层和图示可使用的分层说明。系统所有内容均为**计划实现**，服务于课程演示范围内的山东省城市气象预报资料查询、可视化和基础数据管理。

## 2. 总体分层与调用方向

后续实现将严格按以下单向链路组织：

`Browser → Vue 3（Element Plus、ECharts）→ Axios/REST JSON → Spring Boot → Controller → Service → Mapper（MyBatis-Plus）→ MySQL 8`

| 层次 | 计划职责 | 调用关系 |
| --- | --- | --- |
| Browser | 承载用户选择条件、查看表格和图表、维护资料等交互。 | 发起页面操作，接收 Vue 3 呈现的结果。 |
| Vue 3 | 组织查询、可视化和基础管理页面；Element Plus 承载表单、表格及提示，ECharts 承载趋势图。 | 将已校验的页面条件交给 Axios，并以返回数据更新表格或图表。 |
| Axios/REST JSON | 在前后端之间传递查询条件、管理资料和处理结果。 | 以 REST JSON 请求 Spring Boot，并将 JSON 响应返回 Vue 3。 |
| Spring Boot | 作为后端应用入口，承接 REST JSON 请求。 | 将请求交 Controller 处理并返回处理结果。 |
| Controller | 接收请求参数，完成基础格式检查，组织响应。 | 调用 Service；不直接处理数据持久化。 |
| Service | 承载查询条件、关联校验、时间范围校验、候选业务键判重和管理规则。 | 调用 Mapper；不直接组织页面展示。 |
| Mapper（MyBatis-Plus） | 将 Service 的数据访问请求映射为持久化操作。 | 访问 MySQL 8，并将数据结果返回 Service。 |
| MySQL 8 | 保存城市、预报模型、气象要素和预报记录。 | 向 Mapper 提供持久化数据。 |

各层只面向相邻层调用：浏览器不直接访问后端内部层或数据库；Vue 3 不绕过 Axios/REST JSON；Controller 不绕过 Service；Service 不绕过 Mapper。该边界对应 NFR-M-01 的模块清晰要求，并为 [[09-白板/03-系统总体架构图|系统总体架构图]] 提供文字依据。

## 3. 数据与响应原则

后续查询将以城市、日期/时间范围、气象要素、预报模型为输入（FR-Q-01～FR-Q-04），由 Service 组合条件取得匹配的预报记录。每条记录将保留城市、模型、要素、有效时间、数值和单位，作为表格与图表的共同数据来源，对应 FR-Q-05、FR-V-01、FR-V-04 和 NFR-C-01。

后续管理操作将面向城市、预报模型、气象要素和预报记录四类对象。预报记录处理将检查关联对象存在、有效时间、数值格式以及候选业务键 `(city_id, model_id, element_id, forecast_time)` 的唯一性，对应 FR-M-01～FR-M-05、NFR-C-02、NFR-S-01 与 [[01-立项与需求/08-数据需求|数据需求]]。

## 4. 简单错误返回原则

后续各层将把可预期问题转换为可理解的 REST JSON 结果，再由 Vue 3 显示明确提示。至少覆盖：查询时间范围起止不合法、必填查询条件不完整、关联基础资料不存在、数值不可解析、候选业务键重复，以及无匹配记录。无匹配记录属于正常查询结果，应保留当前查询条件并显示空结果提示；其余校验失败不应继续查询或保存。该原则支撑 FR-Q-05、FR-M-05、NFR-U-02、NFR-S-01。
