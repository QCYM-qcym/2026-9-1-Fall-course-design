# 业务流程设计 V2

## 1. 工作台主链路

1. / 重定向 /weather，加载城市/模型/要素字典，解析 ECMWF/T2M 对应 id 和演示窗口。
2. 校验 modelId、elementId、startTime、endTime；生成缓存键。
3. 命中缓存直接使用；未命中显示 Loading，Axios GET /api/weather/workbench。
4. WeatherQueryController 检查格式，WeatherQueryService 校验关联与范围。
5. ForecastRecordMapper.selectWorkbenchData 通过 XML JOIN 四表、WHERE 过滤模型/要素/范围/山东城市范围，ORDER BY forecast_time、city_id。
6. Service 组装 model、element、升序 times、records，统一响应；空匹配仍 200。
7. 前端只接收最新请求，保存当前完整响应；按 selectedTime 过滤得到地图数据与详情，统一图例。
8. 用户拖动时间轴只重复第 7 步本地过滤，不发送 API，也不访问数据库。
9. 点击城市打开详情；查看趋势携带城市、模型、范围进入 /analysis。

## 2. 简单前端缓存与并发

缓存仅浏览器内存 Map；键是 modelId + elementId + startTime + endTime 的规范化元组（例如序列化数组，避免无分隔拼接冲突），值为完整 Workbench Response。保留最近最多 8 个组合，离开应用/刷新页面清空；不持久化、不用 Redis。

ECMWF → NOAA → ECMWF 同范围可复用缓存。缓存命中不改变参数含义；手动“刷新”忽略并替换当前键缓存。只缓存成功响应（成功空结果可缓存），错误不缓存。

每次改变筛选递增请求序号；只允许最新序号更新页面。CRUD 成功清空全部工作台缓存，递增数据版本，使此前未完成的旧请求即使返回也不能回填缓存。字典变更同步重取下拉；若选中对象已不存在，清选择并提示。趋势与对比不另建缓存，每次进入/提交都查询；管理成功返回趋势必须重新获取。外部工具改库后通过手动刷新/页面重载获取，当前无跨客户端推送一致性承诺。

## 3. 趋势流程

选择城市/模型/范围 → GET /api/weather/trend → Service 校验 → selectTrendData 一次查询 T2M + PRECIP → 按 element_code 分两条升序列 → Service 计算四项统计 → 前端双图、明细表、统计卡来自同一响应。

平均温按实际温度点简单算术平均；max/min 同样基于实际点。降水总量只累加非重叠 3 小时时段量，不累加起报累计值；空序列统计 null。页面标明样本覆盖及缺测，避免把不完整累计当完整窗口实况。

## 4. 对比流程

选择城市/要素/范围 → GET /api/weather/comparison → selectComparisonData 查询 ECMWF/NOAA → Service 依固定模型顺序分组 → 前端时间并集对齐 → 温度双折线或降水分组柱状。某模型无记录仍保留空 series；不补零、不评分。

## 5. 维护后重新查询

四 Tab 管理 → 表单校验 → POST / PUT / DELETE → Service 校验关联、含义与业务唯一性 → BaseMapper 事务写入，数据库约束兜底 → 成功反馈 → 刷新列表、清缓存/旧请求 → 返回趋势重新查询 → 对照保存值、明细表和图表。失败不清成成功状态、不产生部分写入。

引用中的字典不能删除；修改核心编码/单位不能改变已有记录含义。管理记录 GET 是明细管理接口，不承担工作台逐时次请求。

## 6. 异常与追溯

400 参数/格式/数值；404 目标或关联不存在；409 唯一冲突、引用删除/含义变更冲突；500 未预期异常。无匹配 200，与异常严格区分。具体 DTO/VO 和边界以 API V2 为唯一契约，不在不同流程重新定义字段。
